what is orcid
ORCID (Open Researcher and Contributor ID) is a nonproprietary alphanumeric code used to uniquely identify academic authors and researchers. It provides a persistent digital identifier that distinguishes one researcher from another, even if they have similar names, change institutions, or publish under different variations of their name.

Researchers can link their ORCID iD to their publications, grants, and professional activities, which helps with proper attribution and tracking of their work across platforms, publishers, and institutions. Many journals, funding agencies, and universities now require or encourage researchers to have an ORCID iD.

It essentially functions as a unique digital identity for anyone involved in research or scholarly communication.

how to add bibtex to git

To add BibTeX files to Git, you just treat them like any other text file. Here is the typical workflow.

Create or place your BibTeX file
BibTeX files usually have the .bib extension. Put the file inside your Git repository directory, for example:

references.bib


Check repository status
From the root of your repo, run:

git status


You should see the .bib file listed as untracked or modified.

Add the BibTeX file to Git
Stage the file:

git add references.bib


Or add all BibTeX files:

git add *.bib


Commit the file
Commit it like any other file:

git commit -m "Add BibTeX references"


Push to the remote repository
If you use a remote like GitHub or GitLab:

git push


Optional but useful tips:

Keep BibTeX files as plain text
Do not compress or generate them automatically unless necessary. Plain text makes diffs and reviews clean.

Use one shared .bib file for papers or projects
This reduces duplication and merge conflicts.

Avoid auto-sorting on save if collaborating
Some reference managers reorder entries, which can cause noisy diffs.

what does this mean do i need to add a file or is this just something i can tag with git webstie

It means you are expected to **clearly declare the license terms for your work**, not just imply them. On GitHub, the standard and recommended way to do this is by **adding license files to the repository**, not only by tagging or selecting something on the website.

Here is how this breaks down in practical terms.

### Do you need to add a file?

Yes. You should add at least one explicit license file to your repository.

At minimum:

* A `LICENSE` file at the root of the repo

Often also:

* A short license statement in your `README.md` that explains what applies to which parts of the project

Relying only on a GitHub tag or repository setting is not sufficient for academic or reproducible research standards. Many users will clone or download your repo without ever seeing the GitHub UI.

### What does “reproducible research standard” imply?

Victoria Stodden’s recommendation is that **different components of a research project may need different licenses**, but they should be compatible and maximize reuse while preserving attribution.

Typical structure:

* **Code**: permissive open source license
  Examples: MIT, BSD 3-Clause, Apache 2.0
* **Data**: data friendly license
  Examples: CC BY 4.0, CC0
* **Text, figures, media**: content license
  Examples: CC BY 4.0

You can do this in two ways:

1. One main `LICENSE` file plus a section in the README explaining how it applies to code, data, and text.
2. Separate license files such as `LICENSE-code`, `LICENSE-data`, `LICENSE-text`.

### Is tagging on GitHub enough?

No. Selecting a license through GitHub’s interface usually just creates a `LICENSE` file for you. That is fine, but the **file itself** is what matters legally and academically.

If there is no license file:

* Others legally cannot reuse your work.
* Reviewers may flag the project as noncompliant.
* It fails the expectation implied by the assignment text you quoted.

### Minimal compliant setup

If you want the simplest acceptable solution:

1. Add a `LICENSE` file.
2. Add a short “License” section in your README explaining what applies to code, data, and text.
3. Use well known standard licenses, not custom wording.

whats supposed to go in the liscence file

The LICENSE file should contain the full legal text of the license you are applying, not a description or summary.

What goes in it depends on what you are licensing. Below is the standard, accepted way to do this.

If your project is mainly code

Put one complete license text in a file named LICENSE.

Example for MIT License:

Title: MIT License

Copyright line with year and your name

Full MIT license text, word for word

Nothing else. No explanations.

If your project includes code, data, and writing

You have two common options.

Option 1: One LICENSE file plus README clarification

In LICENSE, include the license that applies to the code only.

Example:

MIT License text

Then in README.md, add a section like:

Code is licensed under MIT

Data is licensed under CC BY 4.0

Text and figures are licensed under CC BY 4.0

This is widely accepted and simple.

Option 2: Multiple license files

Create:

LICENSE-code with the full code license text

LICENSE-data with the full data license text

LICENSE-text with the full text/media license text

This is closer to Stodden’s recommendation but not always required.

What should NOT go in LICENSE

Do not summarize the license

Do not mix multiple licenses into one file unless explicitly intended

Do not write custom legal language

Do not just say “see GitHub license tag”

How do you get the correct text?

GitHub’s “Add license” button inserts the correct text automatically

Or copy directly from the official license site:

opensource.org for MIT, BSD, Apache

creativecommons.org for CC licenses

Always use the exact text.
